# Behavioral replay — pre-merge vs post-merge

This is the Phase 7 half of `docs/UPSTREAM_SYNC.md` §5: proof that the upstream sync did not
drop a Blockasaurus addition and did not change the API contract, and an explanation for every
behavioral answer that *did* change.

| | |
| --- | --- |
| Before | `pre-upstream-sync-v0.34.38` → `7e0a40c` |
| After | `main` → `7a34c50` (PR #8 merged) |
| Measured | 2026-09-28 |
| Go | go1.26.4 linux/amd64 |

## How it was measured

Phase 0 recorded that the DNS capture and dashboard screenshots it was supposed to leave behind
were never taken (`baseline-v0.34.38.md`, "Not captured here"), so there was no "before" on disk
to replay against. Instead of replaying against a missing artifact, both trees were **built and
run side by side** and the same probes fired at both:

```bash
git worktree add ../pre-merge pre-upstream-sync-v0.34.38
(cd ../pre-merge/web/ui && npm install && npx vite build) && (cd ../pre-merge && go build -o /tmp/bin/blockasaurus-pre .)
(cd web/ui && npm install && npx vite build)             && go build -o /tmp/bin/blockasaurus-post .
```

Both instances ran on the same host with byte-identical YAML (differing only in ports and store
path) and **byte-identical config-store contents**, seeded through the REST API rather than by
copying a DB, so the seeding itself was part of the smoke test. Verified equal afterwards by
reading both SQLite files directly.

Because upstream configuration lives in the store and not in YAML (`BuildBlockingConfig` /
`BuildCustomDNSConfig` / `BuildUpstreamsConfig` *replace* the YAML sections), a capture taken
before the store is seeded measures almost nothing. Seed first, then **restart** — the store
repairs the `default` client group's group list at open, so the config a fresh boot derives is not
always the config that was live before the restart.

### Delta 1 — `/debug/*` gained `RequireAuth RequireCSRFHeader` in the golden

Registration did not change: `configureDebugHandler` is still `router.Mount("/debug",
middleware.Profiler())` inside the same authenticated `r.Group`, on both sides. What changed is
**chi's reporting**. `chi.Walk` in v5.2.5 omitted the parent group's middlewares for a `Mount`ed
subrouter; v5.3.2 includes them. Reproduced directly:

```
chi v5.2.5:  GET /debug/vars   middleware.NoCache
chi v5.3.2:  GET /debug/vars   main.Guard  middleware.NoCache     <- Guard was always there
```

The v5.3.0 `QUERY` method (RFC 10008) landed in the same window, which is the other half of the
`allMethods` update in `server/api_contract_test.go`.

**The golden is now more complete but reads as more protective than it is.** `RequireAuth`
deliberately passes through any path that is not `/api/*` so the SPA can render and detect auth
state via `/api/auth/session`. Measured on both binaries, unauthenticated:

| Path | pre `7e0a40c` | post `7a34c50` |
| --- | --- | --- |
| `/debug/pprof/` | 200 | 200 |
| `/debug/vars` | 200 | 200 |
| `/debug/pprof/cmdline` | 200 | 200 |
| `/ui/` | 200 | 200 |
| `/api/version` | 401 | 401 |

So: no behavior change, and `/debug` was never gated. That pprof and expvar are reachable
without a session on the API port is a **pre-existing exposure, not merge damage** — see
"Follow-ups" below. It is deliberately not fixed here, because fixing it would change the very
contract this phase exists to hold still.

## 3. DNS behavioral replay

Captured with `go run ./tools/dnsreplay <host:port>` against both instances. Every delta below is
attributable to a named upstream fix on the §6 checklist; there are no unexplained ones.

| # | Probe | Before | After | Cause |
| --- | --- | --- | --- | --- |
| 1 | `printer.lan AAAA` / `TXT` (custom DNS, unmapped type) | NOERROR, empty authority | NOERROR + `SOA printer.lan.` | `802869a` SOA on custom-DNS NOERROR |
| 2 | `singlelabel A` / `AAAA` (fqdnOnly) | **no response at all** — client times out | well-formed NXDOMAIN | `2e5d478` NOTFQDN → NXDOMAIN |
| 3 | any query carrying an OPT record | no OPT in the reply | `OPT udpsize=… do=…` always present | `ff2aae4` always answer EDNS0 with an OPT |
| 4 | EDNS0 client cookie | no OPT at all | OPT present, `options=none` — cookie not echoed | `78d5367` don't pass EDNS0 cookies through |
| 5 | cached negative answer's authority SOA | TTL frozen at 1800 on every repeat | 1788 → 1783 → 1779 over 8s | `190d512` count down cached authority/additional TTLs |
| 6 | everything not explicitly denylisted — `example.com`, `wikipedia.org`, `cloudflare.com`, `fritz.box`, `sub.blocked-domain.test`, … | `0.0.0.0` (blocked) | resolved, or the upstream's own answer | `344d686` allowlist-only mode scope fix — see below |

Delta 2 is worth restating: pre-merge, a single-label query got **no reply**, not a malformed one.

Delta 6 accounts for most of the raw diff, and two of its rows look odd until you follow them
through. `cloudflare.com DNSKEY` goes pre-NXDOMAIN → post-NOERROR because a `zeroIP` block on a
query type with no zero value answers NXDOMAIN — so the pre-merge NXDOMAIN *was* the block.
`cloudflare.com ANY` goes pre-NXDOMAIN → post-**NOTIMP** for that same reason plus one more: once
the query is actually forwarded, `1.1.1.1` answers `ANY` with NOTIMP itself (confirmed by querying
it directly). Neither is Blockasaurus behavior.

### Delta 6 is the one that matters for this fork

Pre-merge, `hasAllowlistOnlyAllowed` put a client into exclusive-allow mode if **any** one of its
groups was allowlist-only. Post-merge, `groupsToCheckForClient` requires **all** of them to be.

The fork reaches that code path by itself. `POST /api/config/domain-entries` with
`entry_type: exact_allow` mints a private group `_d_N` holding exactly one allowlist entry and
auto-adds it to the `default` client group. So on the pre-merge build, **adding one "allow" domain
entry through the web UI silently put every client into allowlist-only mode and blocked the entire
internet**, regardless of how many denylist groups were also present.

Observed on identical config-store contents
(`default = [ads _d_2 _d_3 _d_4 _d_1]`, where `_d_4` is the lone allow entry):

| | queries | blocked | block rate |
| --- | --- | --- | --- |
| pre `7e0a40c` | 240 | 192 | **80.0%** — `example.com`, `wikipedia.org`, `google.com`, `github.com`, `cloudflare.com` all in "top blocked" |
| post `7a34c50` | 240 | 36 | **15.0%** — only the three genuinely denylisted names |

This is an upstream **bug fix landing on a fork-specific footgun**. It is the single most
consequential behavioral change in the whole sync, and it is an improvement.

The Phase 4 `metrics_resolver.go` early-return regression only bites with `prometheus.enable:
false`, so that case was measured on its own: a third instance, prometheus off, same store.
`/api/stats/query-types` went `A: 758 → 890`, `AAAA: 275 → 359` across a traffic run, so the
collector is still fed when the Prometheus block is skipped. Fixed, and confirmed in a running
server rather than only in a test.

Noticed while doing it, unchanged by the merge: `/api/stats` — the dashboard's four headline
tiles — reads `metrics.Reg.Gather()` directly, so with prometheus disabled it reports
`total_queries: 0` while every chart below it is populated from the collector. `server_stats.go`

a delta. Worth an issue if the tiles are meant to work without Prometheus.

The live log viewer streams over the websocket and classifies correctly: `BLOCKED (_d_1: …)`,
`CUSTOM DNS`, `CACHED`, `NXDOMAIN / Special-Use Domain Name`.

Only one console error on either side, on both: a single 401 from the pre-login session probe,
which is the designed first paint.

## Follow-ups

Neither is merge damage; both predate the sync and are recorded here because this is the pass
that measured them.

1. **`/debug/pprof/*` and `/debug/vars` are reachable without a session** on the HTTP API port,
   on both sides, because `RequireAuth` passes through non-`/api/*` paths. Heap, goroutine and
   `cmdline` dumps are readable by anyone who can reach the port. Closing it is a deliberate
   contract change and wants its own issue.
2. **The route golden's middleware column now over-reads as enforcement.** Since chi v5.3.2 it
   lists `RequireAuth` on routes where that middleware is registered but, by design, does not
   enforce. The test's doc comment already says it records what is registered rather than what it
   does; with the `/debug` rows now carrying guard names, that caveat deserves to be visible in
   the golden itself or encoded as an annotation.
